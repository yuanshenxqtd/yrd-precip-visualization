## 1. 系统概述（可用于"系统设计"章的开头）

本系统面向**长三角地区（沪苏浙皖）**，以 56 个降水采集点位为对象，
构建「数据采集 → 数据变换 → 可视化映射 → 用户感知」的完整链路，
并在每一层实现人机交互反馈。

| 维度 | 内容 |
|---|---|
| 数据对象 | 逐小时与逐日降水量（上海 16 个区 + 江苏 13 市 + 浙江 11 市 + 安徽 16 市） |
| 时间跨度 | 日数据 3 年（2023-09 起）；小时数据 1 年（2025-09 起） |
| 数据规模 | 逐小时约 56 万条、逐日约 6.4 万条 |
| 核心能力 | 分级设色地图、IDW 连续降水场、时间轴回放、多尺度趋势与距平、城市对比、点位下钻、自动读图要点 |
| 交互反馈 | ①→可视化映射（换图/换场）②→数据处理（换口径/窗口）③→数据采集（手动采集） |

## 2. 图表选型说明（本文档核心，可直接作为"可视化设计"章）

### 2.1 总原则：先定"要回答什么问题"，再定"用哪个视觉通道"

视觉通道的**定量准确度**是有公认排序的（Cleveland & McGill 实验结论）：

```
位置（共同尺度） > 位置（非共同尺度） > 长度 > 角度/斜率 > 面积 > 体积 > 色相
```

因此本项目遵循一条纪律：**要比较精确数量时用位置/长度；颜色只用来分组、分级或表达连续强度。
绝不要求用户从面积或色相读出精确数值。**

### 2.2 逐图说明

| 图 | 文件 | 回答的问题 | 主用通道 |
|---|---|---|---|
| 分级设色地图 | `RainMap.vue` | 哪个行政区下了多少 | 位置 + 分段色相 |
| 连续降水场 | `FieldMap.vue` | 雨带怎么走、强中心在哪 | 位置 + 连续色相 |
| 逐小时柱状图 | `HourlyTrendChart.vue` | 这一小时多少、什么时候开始 | 长度（高度） |
| 日趋势柱线组合 | `DailyTrendChart.vue` | 日总量与当日最大小时的关系 | 长度 + 位置 |
| 月累计柱状图 | `MonthlyBarChart.vue` | 一年内的季节分布 | 长度 |
| 距平柱状图 | `AnomalyChart.vue` | 比常年多还是少 | 长度 + 零基线方向 |
| 多城市折线 | `MultiLineChart.vue` | 多个城市的时间过程对比 | 位置 + 色相分组 |
| 排行条形图 | `RankingBarChart.vue` | 谁最强、差多少 | 长度（横向） |
| 箱线图 | `BoxplotChart.vue` | 城市之间"日降水的离散程度"差异 | 位置（五数概括） |
| 等级分布环形图 | `LevelDonutChart.vue` | 各降水等级占比 | 角度（仅看构成） |
| 点位矩阵 | `PointMatrix.vue` | 56 个点位此刻的横向对比 | 位置 + 色阶 + 数值标注 |

### 2.3 关键取舍（这几段最适合写进论文的"设计论证"）

**① 为什么地图用"行政区域填色"而不是直接用热力图**
气象业务的发布单元是行政区（"某市发布暴雨预警"），用行政区填色与业务语义一致；
且 56 个离散点直接做点符号会显得稀疏。**代价**是面积大的行政区视觉权重过大（面积错觉），
因此必须配合排行条形图（长度编码）来校准"谁真的最多"。

**② 为什么还要一个连续场**
行政区填色无法表达"雨带"这种**面状连续现象**——同一场雨被行政边界切成色块后，
"雨带从浙东移向苏南"这一过程就消失了。IDW 连续场用颜色连续性表达面状量，
是对区域填色的补充而非替代。**两者在同一面板上提供切换**，是刻意的对照设计。

**③ 为什么排行用横向条形而不是竖向柱**
城市名是中文长标签，竖向柱需要旋转文字或省略；横向条形把类别放在纵轴，标签水平可读。
同时按数值排序（而非按行政区代码），让"排序"本身承载信息。

**④ 为什么箱线图只用来看"离散程度"**
箱线图不擅长读出精确中位数（要读位置），但它能一眼看出"哪个城市降水更集中/更极端"。
与排行条形图分工：条形图答"谁总量多"，箱线图答"谁的日降水更分散"。

**⑤ 为什么环形图只用来"看构成"**
角度/面积编码的定量准确度低，因此环形图旁始终给图例与数量，不要求用户从扇形角度估数值。
若需要精确比较各等级天数，应看表格或条形图。

**⑥ 为什么点位矩阵要同时给"颜色 + 数值"**
56 个点位属于"小而多"的类别，适合小倍数（small multiples）思路。
纯色块只能表达相对强度，**因此每个色块内直接印真实数值**——
颜色负责"扫一眼看趋势"，数值负责"精确读数"，两者互补。

**⑦ 为什么距平图必须画零基线并双向分色**
"距平"的语义是"偏离基准的正负量"，属于发散型数据。
若用单向色阶（如越深越多），负距平会被误读为"少一点的正值"。
因此以零为界、正负分色，并明确标注基准（仅采用 2024/2025 两个完整年）。

**⑧ 刻意不做的事**
- 不用 3D 图（透视会扭曲长度判断）
- 不用双 Y 轴做无关量的叠加（本项目只在"日累计 vs 当日最大小时"这一对强相关量上使用）
- 不做无信息量的入场动画（时间轴回放除外，它的动画本身承载"过程"这一信息）
- 不用饼图/环形图做精确数值比较

## 4. 采集机制

| 项目 | 设计 |
|---|---|
| 点位构成 | 上海 16 个区 + 江苏 13 市 + 浙江 11 市 + 安徽 16 市 = **56** |
| 采集方式 | **单次批量 HTTP 请求**覆盖全部点位（约 4 秒），按点位计量计入免费额度（10000 次/天） |
| 采集间隔 | 30 分钟 |
| 运行形态 | **用户手动启动的前台进程**：关闭窗口即停止，**不做任何开机自启注册** |
| 自愈补采 | 每轮回拉最近 3 天并做**幂等 UPSERT** —— 停机造成的时间缺口在下次启动时自动补齐 |
| 采集审计 | 每次采集（含失败）写入 `collect_log`，界面"采集心跳"即来自该表 |
| 历史回填 | 日数据 3 年；小时数据 1 年；再分析资料有延迟，最近一个月另行补齐 |
| 额度占用 | 最坏情况 56 × 48 = 2,688 次/天 ≈ 免费额度的 **26.9%**（余量 3.7 倍） |

**为什么不做开机自启**：课程设计的演示环境不需要常驻，且常驻会持续消耗额度与电量。
"手动启动 + 自愈补采"在保证数据完整性的前提下把控制权交还给用户 —— 这是一个可写进论文的设计取舍。

## 5. 统计口径（同一个数字，口径不同结论会差很多）

| 项目 | 口径 |
|---|---|
| 降水等级 | 严格按 GB/T 28592-2012 的 **24 小时**口径划分 7 级 |
| 实况 / 预报 | 分开存储与展示（`is_forecast` 标记）；「数据时刻」一律取**实况**最新时刻 |
| 日累计 | 该点位当日 24 个小时值之和；「当日最大小时雨强」单独统计 |
| 距平基准 | **只采用 2024 / 2025 两个完整年**的同期均值 |
| 小时雨强 | 国标未定义小时尺度等级，故只显示真实数值 + 相对强度色阶，**不套用等级名称** |
| 有雨点位 | 区分两种：①"该时刻有雨"②"窗口内累计下过雨"，接口字段分别命名，避免混用 |
| 等级分布计数 | 单位是**点位·天**（日汇总行数），不是日历天数：全区 = 56 个点位合计（56 × 1,143 天 = 64,008 点位·天），只有单点位时 1 行才等于 1 天。**该合计量可解释性差，界面只在聚焦单个点位时展示（单位「天」），全区视图不展示** |
| 区划 vs 点位 | **区划表 = 60 行，采集点 = 56 个**，两者不等：沪苏浙皖 4 个省级条目只用于拼接地图底图边界，本身没有采集点（`is_monitored = false`）。所有统计口径按 56 计算 |

**为什么距平只用两个完整年**：2023 年数据只有 9–12 月，2026 年尚未过完。
把不完整年份混入同期均值会造成严重偏差（例如 2023 年仅四个月会把年均拉低约 2/3）。

## 6. 已知限制（**必须写进论文**，也是答辩最常被追问的地方）

1. **小时数据仅回溯 1 年**（2025-09 起）。因此"时间轴回放""小时雨强分析"只能覆盖近一年；
   日/月/年尺度统计可用完整 3 年。
2. **数据为再分析产品，非地面雨量站实测**。ERA5 是数值模式同化后的网格再分析资料，
   与站点观测存在系统性差异（尤其山区与强对流局地降水）。
   **本系统把它当作"区域性降水态势"使用，不应用于单点精确定量。**
3. **气象预警数据源未接入**。Open-Meteo 不提供中国气象预警，`weather_alert` 表为空、
   `/api/alerts` 返回空数组是预期行为。系统中的"预警统计"是按国标阈值从历史数据中
   筛出的**统计型极端事件**，**不是官方发布的预警信号**。
4. **采集器需要手动启动**。未运行时数据不更新，界面会用黄/红提示条告知数据已多久未更新。
5. **单一数据源，未做多源交叉验证**。数据库结构已支持（`precip_hourly` 带 `source` 字段），
   但尚未接入第二个数据源。
6. **IDW 插值的固有局限**：会低估局地极值（极值被邻近平滑）、不能外推、
   点位稀疏区不可信。它适合"看态势"，不适合"取某点精确值"。
7. **"历史最强"类表述的边界**：受 1 年小时数据限制，此类表述只限定在**近 30 天窗口**内；
   跨年比较只用 2024/2025 两个完整年。摘要中刻意不使用"罕见""破纪录"等超出数据支撑的说法。

## 7. 可视化设计决策

### 7.1 配色

- **降水等级配色**在三处保持一致：后端 `levels.py`、前端 `rainLevels.ts`、设计令牌 `tokens.css`。
  目的是避免"同一等级在不同图里颜色不同"这类低级但伤信任的问题。
- 深色底（`#0a1226` 系）用于大屏与投屏场景，降低长时间观看的视觉疲劳。
- 连续场使用蓝→青→绿→黄→橙→红的分级色阶（符合"冷色=弱、暖色=强"的直觉），
  并且**色阶只表达相对强度**，因为小时雨强没有官方分级。

### 7.2 交互设计：三条反馈回路

参照数据可视化流水线（社会现象 → 采集 → 处理 → 映射 → 感知 → 知识，人机交互贯穿三层）：

| 反馈方向 | 本系统的实现 |
|---|---|
| → **可视化映射** | 连续场/区域着色切换、时间轴播放与拖动、地图缩放平移、模块切换（演示模式浮动条） |
| → **数据处理和变换** | 区域聚焦（改变聚合口径）、统计窗口切换（24h/48h/7天）、时间范围与年份切换、阈值筛选 |
| → **数据采集** | 数据管理页的"立即采集一次"（手动触发新的数据获取） |

### 7.3 联动与聚焦（Relate）

- 全站维护**唯一**的"聚焦点位"状态。点地图区划、排行、点位矩阵、时间轴帧排行，
  都会**同时**：①聚焦该点位 ②打开其详情抽屉。
- 聚焦状态**可见**（页头下方聚焦条写明点位 + 提供"取消聚焦"）、**可撤销**（抽屉按钮反色提示）。
- 设计要点：联动逻辑写在 store 的 `open()` 内部而非各视图 —— **一处改动，四个入口同时生效**，
  避免"某个入口忘了加"的不一致。

### 7.4 按需细节（Details-on-demand）与可信度

任何界面上的数字都能被追问：点开任一工具 → 该点位的逐小时原始值、逐日序列、
等级分布、历史极值、汇总口径。这是"数据可追溯"的直接体现，也是本项目区别于
"只给结论的看板"的关键。

### 7.5 演示模式

隐藏侧边栏与页头、进入全屏、底部保留一条浮动条（时效灯 + 模块切换 + 退出），
并自动播放 2026-08-09~10 大暴雨过程。目的是答辩/汇报时把屏幕让给数据本身。

## 8. 关键实现参数（论文"实现"章可直接引用）

| 参数 | 取值 | 依据 |
|---|---|---|
| 采集间隔 | 30 分钟 | 与 Open-Meteo 更新粒度匹配，额度占用 26.9% |
| 自愈窗口 | 每轮回拉 3 天 | 覆盖一次停机缺口，且不显著增加额度 |
| 分级标准 | GB/T 28592-2012，24 小时口径 | 国标 |
| 距平基准 | 2024 + 2025 同期均值 | 仅这两个年完整 |
| IDW 幂次 | `power = 2` | 反距离平方，气象插值常用 |
| IDW 邻近点 | `k = 12` | 全量 56 点会让远处点贡献过多噪声、抹平强中心 |
| IDW 网格 | `step = 0.12°`，约 56 × 58 ≈ 3,248 格 | 与 56 个点位的平均间距量级匹配 |
| 数据时效阈值 | 新鲜 < 2h / 偏旧 2–24h / 过期 > 24h | 采集间隔 30 分钟，2 小时 = 允许连续 4 次未运行 |
| 接口缓存 | summary 60s / map 120s / trend 300s | 大屏刷新需求与实时性的折中 |
| 数据库 | SQLite + WAL、`synchronous=NORMAL`、`temp_store=MEMORY` | 单机部署、并发读为主 |

## 10. 创新点与亮点表述建议

写论文时建议按"问题 → 做法 → 证据"来组织，以下三条最有说服力：

1. **把"可追溯"作为设计目标而非附属功能**
   → 任何一个展示出来的数字都能点开看到原始小时值；摘要里提到的数据点可以一键跳转到该点位详情，
   两者数值必然一致（实测中"南通市 59.7 mm / 2026-09-27"在摘要与详情中完全吻合）。

2. **对"数据能支撑什么"保持克制**
   → 小时数据只有 1 年，因此"历史最强"只说"近 30 天最强"；自动摘要刻意不使用"罕见""破纪录"。
   这比多画一张图更能体现对数据边界的尊重。

3. **同一份数据的两种读法**
   → 区域填色（业务惯例）+ IDW 连续场（科学表达）并列提供切换，
   承认两者各有局限，而不是假装只有一种正确答案。

## 11. 答辩常见问题与答复要点

| 可能的问题 | 答复要点 |
|---|---|
| 数据是哪来的？可信吗？ | Open-Meteo（ECMWF ERA5 再分析），CC BY 4.0；缺测率 0%、覆盖率 100%。**但要主动说明它是再分析不是雨量站实测** |
| 为什么不用实时气象站数据？ | 站点原始数据需要申请与授权，课程设计条件下采用公开再分析资料是可复现的折中；架构上 `source` 字段已为多源预留 |
